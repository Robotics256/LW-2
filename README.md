# Лабораторная работа № 2

## Основы цифрового моделирования производственных логистических процессов

Проект демонстрирует управление автономным мобильным роботом TurtleBot3 Burger в Gazebo Classic с использованием ROS 2 Humble. В ходе работы строится карта помещения, сохраняются целевые точки, запускается автономная навигация Nav2, а задания роботу передаются через MQTT.

## Цель работы

Изучить основы моделирования производственной логистики и освоить:

- запуск TurtleBot3 в Gazebo;
- ручное управление роботом;
- построение 2D-карты с помощью Cartographer;
- сохранение целевых и промежуточных точек;
- автономную навигацию с помощью Nav2;
- передачу и контроль заданий через MQTT;
- выполнение последовательных маршрутов доставки.

## Требования

- Ubuntu 22.04 LTS (Jammy), предпочтительно Desktop; для WSL2 нужен графический сервер с OpenGL (например, WSLg);
- ROS 2 Humble;
- Python 3 с библиотекой `paho-mqtt`;
- Gazebo Classic 11, RViz, Cartographer и Navigation2;
- доступ к интернету для работы с публичным MQTT-брокером;
- MQTT-клиент, например MQTTX, — при ручной отправке заданий.

## Подготовка к запуску

Команды ниже выполняются из домашней директории, в которой находится папка
`LW-2`. В каждом новом терминале сначала перейдите в неё. Перед первым
запуском выдайте разрешение на выполнение всем shell-скриптам проекта:

```bash
cd "$HOME"
chmod +x ./LW-2/SCRIPTS/*.sh
```

`./` означает текущую директорию: команда `./LW-2/SCRIPTS/...` запускается
из папки, содержащей `LW-2`, а не из самой `LW-2`. Если после распаковки
архива права на запуск сбросились, повторите `chmod`. Python-скрипты
в примерах запускаются через `python3`, отдельное разрешение для них не нужно.

## Установка

Скрипт проверяет Ubuntu 22.04, устанавливает ROS 2 Humble, Gazebo Classic,
`paho-mqtt`, PyYAML, Nav2, Collision Monitor и Cartographer, генерирует учебные
карты и параметры навигации, затем собирает workspace. Для его работы нужны
права `sudo` и интернет; запуск возможен из любой директории.

```bash
./LW-2/SCRIPTS/S1_installRos2.sh
```

## Прибытие в точку

Без явно заданного режима используется `proximity`: робот считается прибывшим,
когда расстояние до точки не превышает **0,30 м**, без конечного доворота.
Это общий стандарт для `navigate_waypoints.py`, MQTT-драйвера, Nav2 через
`S3_startNav.sh` и совместного запуска `start_tb3.sh`.

| Режим | Условие завершения |
|---|---|
| `proximity` (по умолчанию) | расстояние по X/Y не больше 0,30 м, ориентация не учитывается |
| `position` | расстояние по X/Y не больше 0,03 м, ориентация не учитывается |
| `orientation` | расстояние по X/Y не больше 0,03 м, ошибка угла не больше 0,1 рад |

`--mode position` или `--ignore-orientation` явно включает точное
прибытие без доворота. `--orientation` равнозначен `--mode orientation`.
У MQTT-отправителей отсутствие `Mode` сохраняет режим драйвера; явное поле
`Mode` в задании Point имеет приоритет над ним. Для точек загрузки при
необходимости задавайте точный режим отдельно. Треугольник ставится в
фактическом месте остановки, которое может отличаться от координат цели.

Радиус задаётся в `proximity_goal_checker.xy_goal_tolerance` файла
`ros2_ws/src/turtlebot3_simulations/turtlebot3_gazebo/params/warehouse_burger.yaml`
(0.30 метра). Если меняете его, обновите установленный пакет workspace
через `colcon build --symlink-install` и перезапустите Nav2. Отдельного
аргумента `--radius` у отправителей нет.

## Полная последовательность лабораторной

Ниже приведён рабочий порядок из методички для Ubuntu 22.04,
ROS 2 Humble и TurtleBot3 Burger. Окна Gazebo и RViz не закрывайте до конца
соответствующего этапа; каждый блок запускайте в отдельном терминале.

1. Запустите склад для построения карты: лидар виден, ранее сохранённые
   метки автоматически не загружаются. Показ точек включается отдельно
   в программе ручного управления на шаге 3.

   ```bash
   ./LW-2/SCRIPTS/S2_startMapping.sh
   ```

2. Во втором терминале обязательно запустите Cartographer:

   ```bash
   source /opt/ros/humble/setup.bash
   source ./LW-2/ros2_ws/install/setup.bash
   ros2 launch turtlebot3_cartographer cartographer.launch.py use_sim_time:=true
   ```

3. В третьем терминале запустите ручное управление с файлом, в который будут
   записываться точки:

   ```bash
   source /opt/ros/humble/setup.bash
   source ./LW-2/ros2_ws/install/setup.bash
   python3 ./LW-2/SCRIPTS/teleop_keyboard_save.py ./points.txt --show-waypoints
   ```

4. Объедьте все доступные проезды. **Во время этого же объезда одновременно
   расставляйте точки:** останавливайтесь в нужных местах, нажимайте `G` в
   терминале `teleop_keyboard_save.py` и вводите имена (`S2`, `T1`,
   `way_a` и т. п.). Повторно проезжать весь склад после сохранения карты не
   требуется.

   Пример траектории картографирования малого склада: со стоянки S2
   проедьте влево и вправо к стенам зоны стоянки. После выхода со стоянки
   поверните **сначала влево**, поднимитесь по западному проходу к T1,
   затем посетите T2, проедьте проход B справа налево, проход A слева
   направо, посетите T3, затем выезжайте из зоны отгрузки и поверните
   влево по южному проходу. Переход между проходами B и A расположен
   справа от линии первоначального подъёма по западному проходу.

   ![Пример траектории картографирования малого склада](docs/warehouse/small_mapping_trajectory.png)

   [Схема в формате SVG](docs/warehouse/small_mapping_trajectory.svg).

   **Расстановка сохраняемых точек:** в каждом проходе A и B создайте
   по четыре точки загрузки напротив стеллажей с номерами **1, 3, 5 и 7**.
   Сами стеллажи остаются на месте: сохранять отдельную точку напротив
   каждого из семи стеллажей не требуется.

   ![Пример расстановки точек загрузки, выгрузки, стоянки и промежуточных точек](docs/warehouse/small_waypoint_layout.png)

   [Схема расстановки точек в формате SVG](docs/warehouse/small_waypoint_layout.svg).

   | Точки на схеме | Что сохранить в файл точек |
   |---|---|
   | A1–A4 | `A1`, `A2`, `A3`, `A4` в проходе A, напротив стеллажей 1, 3, 5 и 7 |
   | B1–B4 | `B1`, `B2`, `B3`, `B4` в проходе B, напротив стеллажей 1, 3, 5 и 7 |
   | T1–T3 | `T1`, `T2`, `T3` у рабочих зон |
   | S1–S3 | **Три отдельные точки стоянки:** `S1`, `S2`, `S3` |
   | P1–P12 | Пример промежуточных точек `P1`–`P12` в проходах и у поворотов для построения графа |

   Нумерация P-точек идёт по порядку объезда: от `P1` у выхода со стоянки
   влево к `P2`, затем вверх по западному проходу к T1 и T2,
   через проходы B и A к южному проходу и T3. `P6` и `P7` расположены
   ниже T1 и T2 соответственно; под центральной перегородкой точки нет.
   Точки `P2`, `P3`, `P4` и `P5` выровнены в одну колонку слева.

   Имена A, B, P, S вводите латинскими буквами; регистр должен совпадать
   с именами в программе доставки. Не путайте точки загрузки `A1`–`A4`
   и `B1`–`B4` с подписями физических стеллажей вида `A1_1` и `B2_7`.
   Координаты всех точек записывайте при объезде собственной SLAM-карты.
   Параметр `--show-waypoints` в команде шага 3 включает зелёные метки
   в Gazebo и RViz: отображаются точки из выбранного файла и новые точки
   после сохранения. Без этого параметра запись работает, но метки скрыты.

5. Когда карта построена и точки записаны, сохраните карту в отдельном
   терминале. Будут созданы `./warehouse_map.yaml` и
   `./warehouse_map.pgm`:

   ```bash
   source /opt/ros/humble/setup.bash
   source ./LW-2/ros2_ws/install/setup.bash
   ros2 run nav2_map_server map_saver_cli -f ./warehouse_map \
     --ros-args -p use_sim_time:=true
   ```

   После успешного сохранения остановите через `Ctrl+C` Cartographer,
   `teleop_keyboard_save.py` и симуляцию. Закройте оставшиеся окна RViz и
   Gazebo.

6. Запустите новую чистую симуляцию, явно указав сохранённый файл точек, а
   затем в другом терминале запустите Nav2 с сохранённой картой:

   После загрузки карты Nav2 ещё не знает, где находится робот в её системе
   координат. Поэтому в RViz необходимо указать его начальную позу и направление.

   ```bash
   ./LW-2/SCRIPTS/S2_startSim.sh points_file:=./points.txt
   ```

   ```bash
   ./LW-2/SCRIPTS/S3_startNav.sh ./warehouse_map.yaml
   ```

   После появления карты в RViz обязательно выберите **2D Pose Estimate** и
   укажите фактическое начальное положение и направление робота на карте.

7. Проверьте автономное движение напрямую через Nav2, без MQTT. Путь к файлу,
   имя точки и предельная скорость задаются в команде:

   ```bash
   source /opt/ros/humble/setup.bash
   source ./LW-2/ros2_ws/install/setup.bash
   python3 ./LW-2/SCRIPTS/navigate_waypoints.py \
     ./points.txt T1 --speed 0.15 --trail НОМЕР_ВАРИАНТА
   ```

   В каждом новом терминале сначала подключите оба файла `setup.bash`. Без
   этого Python не найдёт библиотеку ROS 2 `rclpy` и выведет
   `ModuleNotFoundError: No module named 'rclpy'`.

   Скорость должна быть больше `0` и не превышать `0.30` м/с. Несколько имён выполняются
   последовательно, например `S2 way_a T1`.

8. После проверки без MQTT запустите MQTT-драйвер и отправляйте задания из
   MQTTX либо MQTT-скриптами:

   ```bash
   source /opt/ros/humble/setup.bash
   source ./LW-2/ros2_ws/install/setup.bash
   python3 ./LW-2/SCRIPTS/mqtt_driver.py --trail НОМЕР_ВАРИАНТА
   ```

9. Сначала выполните доставку из Python-кода на **хостовой системе** вне
   Ubuntu/WSL. Настройте одинаковые MQTT-параметры в хостовой и Ubuntu-копии.
   В `sent_many_task.py` изучите и измените `main()`; используйте её как основу
   задания. В начале этого файла задайте `MQTT_BROKER`, `MQTT_PORT`,
   `WORKSPACE` и `MODULE_NAME`: адрес брокера, порт, рабочую область и имя
   робота в MQTT. Они явно передаются в `TaskClient(...)`. У драйвера в
   Ubuntu задайте такие же значения в `SCRIPTS/lw2_config.py`.
   Замените примерные имена P1, A2, T1, S2 на сохранённые у вас точки.
   Из PowerShell Windows, в папке, содержащей LW-2:

   ```powershell
   py -m pip install paho-mqtt
   py .\LW-2\SCRIPTS\sent_many_task.py
   ```

10. Альтернатива для проверки готовой последовательности из консоли хоста:

    ```powershell
    py .\LW-2\SCRIPTS\sent_many_task_cli.py P1 A2 up T1 down S2 --points-file .\points.txt
    ```

    `up` — загрузка и красный треугольник, `down` — выгрузка и синий.
    Путь points.txt здесь относится к Windows. Каждый шаг ждёт статуса 0;
    при ошибке или тайм-ауте дальнейшие шаги не отправляются. Промежуточные
    точки можно вставлять между шагами. В отчёте покажите обе грузовые метки.

Перед любой отправкой проверьте, что Nav2 активен, начальная поза задана и в
`./points.txt` есть запрошенное имя. Карта и точки создаются за один общий
объезд, а затем загружаются для локализации и автономного движения.

## 1. Запуск симуляции

Запуск:

```bash
./LW-2/SCRIPTS/S2_startSim.sh
```

Каждый следующий компонент запускайте в отдельной вкладке терминала, не закрывая Gazebo и не останавливая запущенный в консоли скрипт.

### Учебные миры

Параметр `world` выбирает планировку при запуске. Это имя Gazebo-мира, чтобы
не путать его с аргументом `map:=...` у Nav2.

| Значение | Мир | Статическая карта Nav2 |
|---|---|---|
| `large` | Большой склад 12 × 10 м, зоны A и B, T1–T4 | `warehouse.yaml` |
| `small` | Малый склад 6 × 10 м, зона A, T1/T2/T4 | `warehouse_small.yaml` |
| `stage4` | Штатный пример `turtlebot3_dqn_stage4` | карту нужно построить Cartographer |
| `automotive` | Склад автозавода 72 × 48 м | `warehouse_automotive.yaml` |

```bash
./LW-2/SCRIPTS/S2_startSim.sh world:=large
./LW-2/SCRIPTS/S2_startSim.sh world:=small
./LW-2/SCRIPTS/S2_startSim.sh world:=stage4
./LW-2/SCRIPTS/S2_startSim.sh world:=automotive
```

`small` — значение по умолчанию. Для большого варианта явно передайте
`world:=large`.
В запуске симулятора также допустимо `map:=small` как синоним `world:=small`.
В команде Nav2 `map:=...` по-прежнему означает путь к файлу `.yaml`.

Для SLAM и записи точек запускайте `S2_startMapping.sh`; он эквивалентен
`S2_startSim.sh mode:=mapping`. Для автозавода:

```bash
./LW-2/SCRIPTS/S2_startMapping.sh world:=automotive
```

`mode:=mapping` показывает лучи лидара и скрывает сохранённые метки;
`mode:=navigation` (по умолчанию) скрывает лучи и показывает метки.
Сам `/scan` работает в обоих режимах. `lidar_visual:=true|false` и
`show_waypoints:=true|false` явно переопределяют отображение.
Для показа зелёных меток при ручной записи запускайте teleop с
`--show-waypoints`, как в примерах ниже. Без параметра точки сохраняются
в файл, но не рисуются.

Совместный запуск Gazebo, Nav2 и JSON MQTT-драйвера:

```bash
./LW-2/SCRIPTS/start_tb3.sh ./warehouse_map.yaml --points-file ./points.txt --trail НОМЕР_ВАРИАНТА
./LW-2/SCRIPTS/start_tb3.sh ./automotive_map.yaml \
  --world automotive --points-file ./points_automotive.txt --trail НОМЕР_ВАРИАНТА
```

Без пути карты этот скрипт использует эталонную карту выбранного мира;
точки должны относиться к той же системе координат. Для `stage4` карта
обязательна. После запуска задайте **2D Pose Estimate** в RViz.
`--orientation` включает сохранённый конечный угол, `--headless` отключает
окна Gazebo и RViz. Подробнее об автозаводе: [AUTOMOTIVE.md](docs/warehouse/AUTOMOTIVE.md).

### Большой учебный склад

Большой склад **12 × 10 м** содержит общую стоянку на семь
роботов, две зоны по три стеллажа, приёмка, конвейер, станок и отгрузка.
Стеллажи состоят из квадратных секций 0,5 × 0,5 м. Проходы между ними — 0,8 м;
боковые основные проезды — 2,1 м. Все стеллажи доходят до центральной стены;
A2 и B2 двойные: по два ряда коробок.
Новые стенки разделяют складские зоны, рабочие пункты и стоянку / отгрузку.
Между севером и югом доступны западный и восточный обходы; центрального сквозного
проезда нет. Южный поперечный проход — 1,35 м, северный — минимум 1,1 м.

![План малого склада](docs/warehouse/small_warehouse_plan.svg)

[Размеры, точки, маршруты, эталонная карта и расширение для группы](docs/warehouse/README_warehouse.md).
План и инструкция малого варианта: [малый склад](docs/warehouse/SMALL.md).
После обновления проекта пересоберите пакет:

```bash
source /opt/ros/humble/setup.bash
cd ./LW-2/ros2_ws
colcon build --symlink-install --packages-select turtlebot3_gazebo
cd "$HOME"
```

Обычный и headless-запуск Burger (модель по умолчанию):

```bash
./LW-2/SCRIPTS/S2_startSim.sh
./LW-2/SCRIPTS/S2_startSim.sh gui:=false
```

В режиме навигации лучи скрыты по умолчанию. Чтобы явно показать их:

```bash
./LW-2/SCRIPTS/S2_startSim.sh lidar_visual:=true
```

Burger — модель по умолчанию во всех скриптах. Не смешивайте модели между
терминалами одной симуляции.
Штатный запуск создаёт **одного** робота на месте P2; семь мест предусмотрены
для дальнейшей групповой лабораторной. Построение собственной карты и запись
точек выполняются по разделам ниже.

## 2. Ручное управление

```bash
python3 ./LW-2/SCRIPTS/teleop_keyboard_save.py ./points.txt --show-waypoints
```

Лимиты ручного управления находятся в `SCRIPTS/lw2_config.json`:

```json
"teleop": {
  "max_linear_speed": 0.15,
  "max_angular_speed": 0.8
}
```

Это максимальные абсолютные команды в м/с и рад/с: ограничения действуют
при движении вперёд, назад и поворотах в обе стороны. Дополнительно действует
предел модели робота. Значение `0` отключает движение по соответствующей оси.
Изменения применяются после перезапуска teleop; другой конфиг можно выбрать
через `--config ПУТЬ.json`.

Для ручного движения с лидарной защитой используйте флаг
`--collision-monitor`:

```bash
python3 ./LW-2/SCRIPTS/teleop_keyboard_save.py --collision-monitor ./points.txt --show-waypoints
```

Скрипт запускает отдельный `nav2_collision_monitor` и направляет команды по
цепочке `/cmd_vel_teleop → Collision Monitor → /cmd_vel`. В зоне до 0,6 м
перед роботом скорость уменьшается до 25 %, а в ближней зоне до 0,35 м спереди
робот останавливается. Настройки зон находятся в
`SCRIPTS/teleop_collision_monitor.yaml`. Этот режим защищает именно команды
ручного управления и может работать одновременно с Nav2, у которого свой
контур команд.

Скрипт сам подключает ROS 2 Humble и workspace. По умолчанию он управляет Burger.
Перед вызовом `G` должны работать Cartographer либо Nav2: точки сохраняются в
системе координат `map`, которую Nav2 использует для целей.

```bash
TURTLEBOT3_MODEL=burger python3 ./LW-2/SCRIPTS/teleop_keyboard_save.py ./points.txt --show-waypoints
```

Клавиши управления:

| Клавиша | Действие |
|---|---|
| `W` / `X` | увеличить / уменьшить линейную скорость |
| `A` / `D` | увеличить / уменьшить угловую скорость |
| `S` или `Space` | остановить робота |
| `G` | остановиться и сохранить текущую позу под заданным именем |
| `Ctrl+C` | завершить программу |

Клавиши в программе обрабатываются в нижнем регистре. Если путь не указан,
точки добавляются в файл `points.txt` в домашней директории. В примерах
путь задан явно как `./points.txt`:

```bash
python3 ./LW-2/SCRIPTS/teleop_keyboard_save.py ./points.txt --show-waypoints
```

Формат строки в файле:
`имя, map_x, map_y, orientation_z, orientation_w, gazebo_x, gazebo_y`.
Последние две координаты нужны для отображения меток в Gazebo. Nav2 по
умолчанию использует `map_x`, `map_y`; сохранённый угол учитывается при
явном выборе `--orientation` или `Mode: "orientation"`.

После `G` робот получает команду остановки. Координаты считываются после
ввода имени: TF в `map` запрашивается на момент измерения Gazebo. Если TF
отсутствует или старше 0,5 с, точка не записывается и выводится причина.
Без сервиса Gazebo сохраняется свежая поза только в `map` (пять полей).

Старое сравнение с медианой разностей `map − Gazebo` удалено: оно ошибочно
предполагало постоянное смещение без поворота и блокировало запись при
коррекциях SLAM. Ограничение истории последними пятью точками не исправляет
это предположение. Свежесть TF не подтверждает правильность самой локализации:
при неверной позе AMCL её нужно исправить в RViz. После изменения системы
координат карты ранее записанные точки автоматически не пересчитываются.

## 3. Построение и сохранение карты

Запустите Cartographer:

```bash
export TURTLEBOT3_MODEL=burger
source /opt/ros/humble/setup.bash
source ./LW-2/ros2_ws/install/setup.bash
ros2 launch turtlebot3_cartographer cartographer.launch.py use_sim_time:=true
```

С помощью `teleop_keyboard_save.py` объедьте всё помещение. В RViz должны
отобразиться стены, препятствия и доступные проходы. Во время этого же объезда
останавливайтесь в нужных местах, нажимайте `G` и сохраняйте именованные точки
в `./points.txt`. Таким образом, карта и точки создаются одновременно — второй
объезд после запуска Nav2 не нужен.

Рекомендуемый набор имён:

- `S2` — место стоянки;
- `T1` и `T2` — зоны загрузки и выгрузки;
- `way_a`, `way_e` и другие `way_*` — промежуточные точки маршрутов.

Когда объезд и расстановка точек закончены, сохраните карту:

```bash
source ./LW-2/ros2_ws/install/setup.bash
ros2 run nav2_map_server map_saver_cli -f ./warehouse_map \
  --ros-args -p use_sim_time:=true
```

Будут созданы `./warehouse_map.pgm` и `./warehouse_map.yaml`. После успешного
сохранения остановите через `Ctrl+C` Cartographer, ручное управление и
симуляцию; закройте RViz и Gazebo.

## 4. Перезапуск сцены и загрузка точек

Запустите сцену заново и укажите созданный на предыдущем этапе файл:

```bash
./LW-2/SCRIPTS/S2_startSim.sh points_file:=./points.txt
```

`S2_startSim.sh` передаёт путь загрузчику меток. Точки с сохранёнными
`gazebo_x`, `gazebo_y` отображаются в сцене автоматически; дополнительно они
публикуются в RViz в топике `/waypoints`. Другой файл можно выбрать заменой
значения `points_file:=`. Альтернативно путь можно передать переменной окружения
`TB3_POINTS_FILE`.

Имена чувствительны к регистру и должны точно совпадать с именами, которые
затем передаются в прямых и MQTT-заданиях.

## 5. Запуск автономной навигации

После запуска Gazebo по разделу 4 запустите Navigation2 в другом терминале.
MQTT-драйвер добавляется только после проверки обычной отправки цели.

### Терминал 2 — Navigation2

При каждом запуске S3 сначала останавливает предыдущую навигацию LW-2
текущего пользователя в том же `ROS_DOMAIN_ID`, включая оставшиеся контейнеры
Nav2 и RViz. Если процессы не отвечают на обычную остановку, скрипт завершает
их принудительно. Gazebo продолжает работать. Поэтому повторный запуск S3
также перезапускает уже работающую навигацию.

```bash
./LW-2/SCRIPTS/S3_startNav.sh ./warehouse_map.yaml
```

После появления карты в RViz обязательно задайте начальную позицию робота
инструментом **2D Pose Estimate**. Положение должно соответствовать фактической
позиции робота на карте, а стрелка — его направлению.

### Терминал 3 — цель напрямую, без MQTT

После того как Localization и Navigation в панели Nav2 перешли в состояние
`active`, отправьте точку из `points.txt`:

```bash
source /opt/ros/humble/setup.bash
source ./LW-2/ros2_ws/install/setup.bash
python3 ./LW-2/SCRIPTS/navigate_waypoints.py ./points.txt T1 --trail НОМЕР_ВАРИАНТА
```

Позиционные параметры команды:

| Параметр | Значение в примере | Описание |
|---|---|---|
| `points_file` | `./points.txt` | путь к файлу сохранённых точек |
| `points` | `T1` | одно или несколько имён точек для последовательного маршрута |

Дополнительные параметры:

| Параметр | Значение | Описание |
|---|---|---|
| `--mode position` | явно | прибытие по X/Y с допуском 0.03 м, без конечного доворота |
| `--orientation`, `--mode orientation` | флаг / режим | также достигать сохранённого угла с допуском 0.1 рад |
| `--mode proximity` | по умолчанию | прибытие в радиусе 0.3 м, без конечного доворота |
| `--ignore-orientation` | совместимый флаг | явно выбрать точный режим `position` |
| `--speed ЧИСЛО` | `0.20` м/с по умолчанию | максимальная линейная скорость; допустимо `0 < speed <= 0.30` м/с |
| `--trail НОМЕР_ВАРИАНТА` | след включён по умолчанию | выбрать цвет следа; без номера он синий, с номером — из `SCRIPTS/lw2_config.json` |
| `--no-trail` | флаг | отключить след движения |

Например, для скорости `0.15` м/с:

```bash
python3 ./LW-2/SCRIPTS/navigate_waypoints.py \
  ./points.txt T1 --speed 0.15 --trail НОМЕР_ВАРИАНТА
```

Для последовательного маршрута перечислите несколько имён точек:

```bash
python3 ./LW-2/SCRIPTS/navigate_waypoints.py \
  ./points.txt S2 way_a T1 --speed 0.15 --trail НОМЕР_ВАРИАНТА
```

Перед первым использованием этого режима перезапустите Nav2, чтобы он загрузил
дополнительный проверяющий модуль цели.

Флаг `--trail` можно объединять с другими параметрами:

```bash
python3 ./LW-2/SCRIPTS/navigate_waypoints.py ./points.txt T1 --trail НОМЕР_ВАРИАНТА
```

Вместо `НОМЕР_ВАРИАНТА` подставьте свой номер варианта от 1 до 21 (без скобок), например `--trail 7` для варианта 7.
Все 21 цвета хранятся в разделе `trail_colors` общего файла
`SCRIPTS/lw2_config.json` в формате RGB от `0` до `1`; их можно свободно
изменить. Другой общий конфиг можно передать через `--config /путь/config.json`.

След записывается от положения робота в момент отправки цели до завершения
движения и остаётся видимым до перезапуска симуляции. Метки следа не имеют
коллизий и не влияют на лидар или Nav2.

Во всех трёх режимах автоматическое аварийное движение задним ходом отключено: если
Nav2 не сможет построить или выполнить маршрут, робот остановится и программа
сообщит об ошибке навигации.

Для складских проходов радиус распространения стоимости препятствий в локальной
и глобальной costmap уменьшен до `0.35 м`. Физический радиус Burger остаётся
`0.15 м`; после изменения параметров перезапустите Nav2.

Скрипт не изменяет начальную позу AMCL и ждёт, пока она будет задана в RViz.

### Терминал 4 — MQTT-драйвер

Настройки MQTT-драйвера и значения по умолчанию консольных отправителей находятся в
`SCRIPTS/lw2_config.py`. Их можно переопределить переменными окружения
`TB3_MQTT_BROKER`, `TB3_MQTT_PORT`, `TB3_MQTT_WORKSPACE`, `TB3_MQTT_NAME`,
`TB3_MQTT_USERNAME` и `TB3_MQTT_PASSWORD`. Установите одинаковые значения
в терминалах драйвера и отправителей.

В проекте по умолчанию используются вариант 21, пространство `space_v21` и робот `amr1_v21`.

Драйвер по умолчанию читает файл `points.txt` в домашней директории,
независимо от текущей директории. В примерах эта директория выбрана
командой `cd "$HOME"`.

```bash
cd "$HOME"
source /opt/ros/humble/setup.bash
source ./LW-2/ros2_ws/install/setup.bash
python3 ./LW-2/SCRIPTS/mqtt_driver.py --trail НОМЕР_ВАРИАНТА
```

По умолчанию MQTT-драйвер принимает прибытие по X/Y. Чтобы требовать
сохранённый конечный угол для сообщений без поля `Mode`:

```bash
python3 ./LW-2/SCRIPTS/mqtt_driver.py --orientation --trail НОМЕР_ВАРИАНТА
```

Поле `Mode` в конкретном `Point` имеет приоритет над параметром драйвера.
При явном выборе режима в отправителе он записывается в JSON-сообщение.
Пунктирный след включён по умолчанию; можно выбрать цвет или отключить его:

```bash
python3 ./LW-2/SCRIPTS/mqtt_driver.py --trail НОМЕР_ВАРИАНТА
python3 ./LW-2/SCRIPTS/mqtt_driver.py --no-trail
```

Используемые MQTT-параметры:

| Параметр | Значение по умолчанию |
|---|---|
| Брокер | `broker.emqx.io:1883` |
| Топик команд | `space_v21/devices/in/delivery/amr1_v21` |
| Топик статусов | `space_v21/devices/out/delivery/amr1_v21` |

Статусы задания: `0` — выполнено, `1` — выполняется, `2` — ошибка, `3` — робот занят и задание отклонено.

Драйвер также принимает `status`, `history`, `Stop` и цепочки заданий в
JSON. [Полный формат, ответы и примеры](MQTT_JSON.md).

### Загрузка и выгрузка

MQTT-драйвер принимает штатные типы задач `Upload` (загрузка робота) и
`Download` (выгрузка). Для удобства также принимаются псевдонимы `Load` и
`Unload`. Операция не прерывает текущую навигацию и использует ту же схему
статусов и идемпотентность по `Task.Id`, что и задача `Point`.

При `Upload` в текущей позиции остаётся красный треугольник, а верхняя часть
робота становится красной. При `Download` остаётся синий треугольник, а
красная накладка снимается. Треугольники расположены выше меток пути и
сохранённых точек, не имеют коллизий и сохраняются до перезапуска Gazebo.

Эффекты и цвета следа собраны в одном пользовательском файле
`SCRIPTS/lw2_config.json`. Эффекты груза включаются независимо в разделе
`cargo`:

```json
{
  "cargo": {
    "floor_markers_enabled": true,
    "robot_color_enabled": true
  },
  "trail_colors": {
    "1": [0.90, 0.10, 0.10]
  }
}
```

Другой конфиг можно указать через
`mqtt_driver.py --config /путь/к/config.json`. Старое имя аргумента
`--cargo-config` сохранено как совместимый псевдоним.

### Дополнительные параметры запуска

| Команда | Необязательные параметры |
|---|---|
| `S2_startMapping.sh`, `S2_startSim.sh` | `world:=small/large/automotive/stage4`, `points_file:=ПУТЬ`, `lidar_visual:=true/false`, `show_waypoints:=true/false` |
| `teleop_keyboard_save.py ФАЙЛ` | `--show-waypoints`, `--collision-monitor`, `--config ФАЙЛ.json` |
| `S3_startNav.sh КАРТА.yaml` | `points_file:=ПУТЬ`, `--mode РЕЖИМ`, `--orientation`, `--initial-pose X Y YAW` (map, метры и радианы) |
| `navigate_waypoints.py ФАЙЛ ТОЧКИ` | `--mode РЕЖИМ`, `--orientation`, `--speed 0.15` (максимум 0.30), `--trail НОМЕР_ВАРИАНТА` (1–21), `--no-trail`, `--config ФАЙЛ.json` |
| `mqtt_driver.py` | `--points-file ПУТЬ`, `--mode РЕЖИМ`, `--orientation`, `--trail НОМЕР_ВАРИАНТА`, `--no-trail`, `--config ФАЙЛ.json`, `--task-history 100`, `--max-tasks 100` |
| `sent_one_task.py`, `sent_many_task_cli.py` | `--points-file ПУТЬ`, `--mode РЕЖИМ`, `--orientation`, `--ignore-orientation`; у `sent_many_task_cli.py` также `--broker`, `--port`, `--workspace`, `--name` |
| `start_tb3.sh КАРТА.yaml` | `--world МИР`, `--points-file ПУТЬ`, `--mode РЕЖИМ`, `--orientation`, `--headless`, `--trail НОМЕР_ВАРИАНТА`, `--no-trail` |

Вместо РЕЖИМ укажите `proximity`, `position` или `orientation`.
Для уже собранной Ubuntu-копии после обновления только SCRIPTS пересборка
не нужна. Перед установкой целей в RViz всё равно задайте 2D Pose Estimate.

## 6. Отправка задания через MQTT

Отправитель MQTT не требует ROS 2: задание можно публиковать как из WSL, так и
с хоста. MQTT-драйвер, принимающий задание и передающий его Nav2, остаётся
запущенным в WSL. На хосте используйте MQTTX или Python-скрипты из копии
проекта с доступом к тому же файлу `points.txt`.

### Через MQTTX

Подключитесь к `mqtt://broker.emqx.io:1883`, подпишитесь на топик статусов и опубликуйте в топик команд сообщение без флага `Retain`:

```json
{
  "Module": {
    "Name": "amr1_v21",
    "Type": "delivery",
    "UID": 12346,
    "Data": {
      "Task": {
        "Id": 67890,
        "Type": "Point",
        "Data": "S2"
      }
    }
  }
}
```

Для каждого нового сообщения изменяйте `UID` и `Task.Id`. Поле `Task.Data` должно содержать имя существующей точки из `points.txt`.

Пример загрузки (для выгрузки замените `Upload` на `Download`):

```json
{
  "Module": {
    "Name": "amr1_v21",
    "Type": "delivery",
    "UID": 12347,
    "Data": {
      "Task": {
        "Id": 67891,
        "Type": "Upload",
        "Data": ""
      }
    }
  }
}
```

### Через MQTT-скрипты Python

Отправка одного задания:

```bash
python3 ./LW-2/SCRIPTS/sent_one_task.py S2
python3 ./LW-2/SCRIPTS/sent_one_task.py S2 --orientation
```

Скрипт отправляет одно задание. Последний аргумент — существующее имя точки из
`./points.txt`; например, замените `S2` на `T1`.

Сначала изучите и запустите пример доставки в `sent_many_task.py`:

```bash
python3 ./LW-2/SCRIPTS/sent_many_task.py
```

Класс `TaskClient` находится в `SCRIPTS/task_client.py`; пример и консольный
отправитель подключают его через `from task_client import TaskClient`.
Для своего управляющего файла в `SCRIPTS` используйте тот же импорт.
В начале `sent_many_task.py` студенты изменяют настройки MQTT прямо в коде:

```python
MQTT_BROKER = "broker.emqx.io"
MQTT_PORT = 1883
WORKSPACE = "space_v21"
MODULE_NAME = "amr1_v21"
```

Они передаются при создании клиента:

```python
client = TaskClient(broker=MQTT_BROKER, port=MQTT_PORT,
                    workspace=WORKSPACE, module_name=MODULE_NAME)
```

Топики и имя модуля в заданиях формируются из этих значений. У драйвера
в Ubuntu настройки должны совпадать. Для консольного отправителя задайте
`--broker АДРЕС --port 1883 --workspace РАБОЧАЯ_ОБЛАСТЬ --name ИМЯ_РОБОТА`.
Без этих аргументов CLI использует значения из `lw2_config.py` и окружения.

Имена точек задаются в `main()`. Перемещения расписаны явно, без цикла:
P1 → A2 → up → T1 → down → S2. Замените их своими точками. Эту функцию рекомендуется
использовать как основу задания. На Windows-хосте запускайте через `py`.

Альтернативный консольный отправитель `sent_many_task_cli.py` принимает
точки и грузовые команды в одном списке:

```bash
python3 ./LW-2/SCRIPTS/sent_many_task_cli.py \
  P1 A2 up T1 down S2 --points-file ./points.txt
```

`up` — загрузка (`Upload`), `down` — выгрузка (`Download`). Слова `up` и
`down` в нижнем регистре зарезервированы и не могут служить именами точек.
Каждый шаг ждёт статуса 0. При ошибке дальнейшие шаги не отправляются.
Файл точек нужен только если последовательность содержит перемещения.
На хосте укажите путь к доступной там копии points.txt.

Последовательный маршрут только из точек:

```bash
python3 ./LW-2/SCRIPTS/sent_many_task_cli.py S2 T1 way_a T2 S2
```

У sent_one_task.py и sent_many_task_cli.py есть `--mode position|orientation|proximity` и
сокращение `--orientation`; без явного режима используется настройка драйвера, стандартно `proximity`.

Аргументы задают последовательность точек. Скрипт ждёт статус `0` для каждой
точки перед отправкой следующей; тайм-аут одного задания — 300 секунд.

### Включение загрузки и выгрузки в программу доставки

У `TaskClient` из `task_client.py` есть метод `send_cargo_task("load")`
для загрузки и `send_cargo_task("unload")` для выгрузки. Эти вызовы отправляют
штатные задания `Upload` и `Download`. После каждой операции нужно дождаться
`wait_task_success`: публикация сообщения сама по себе не подтверждает
появление треугольника. При ошибке Gazebo доставка должна прерываться.

```python
from task_client import TaskClient

client = TaskClient(broker="broker.emqx.io", port=1883,
                    workspace="space_v21", module_name="amr1_v21")
try:
    task_id = client.send_move_task("T1")
    client.wait_task_success(task_id, timeout=300)
    task_id = client.send_cargo_task("load")
    client.wait_task_success(task_id, timeout=30)

    task_id = client.send_move_task("T2")
    client.wait_task_success(task_id, timeout=300)
    task_id = client.send_cargo_task("unload")
    client.wait_task_success(task_id, timeout=30)
finally:
    client.close()
```

Замените `T1` и `T2` именами своих точек. Промежуточные точки маршрута
также выполняйте последовательно с ожиданием успешного завершения.
Управляющая программа работает на хосте, MQTT-драйвер и Gazebo — в Ubuntu.
На хосте нужны Python, `paho-mqtt` и модули из `SCRIPTS`; ROS 2 не требуется.
Параметр `--points-file` у драйвера и пути в командах Ubuntu относятся к Ubuntu.
Для CLI-отправителей на хосте указывайте путь к доступной там копии points.txt.

В Gazebo после загрузки остаётся красный треугольник, после выгрузки — синий.
Отправляйте грузовую команду только после подтверждённого прибытия: драйвер
разрешает отдельное грузовое задание и во время движения, поэтому ранняя
отправка оставит метку в промежуточном месте. В отчёте покажите обе метки
после отъезда робота и статусы `0` соответствующих заданий.

Ручная активация загрузки и выгрузки:

```bash
python3 ./LW-2/SCRIPTS/manual_load.py
python3 ./LW-2/SCRIPTS/manual_unload.py
```

То же через общий отправитель: `send_cargo_command.py load` и
`send_cargo_command.py unload`. Эти тестовые скрипты не требуют ROS 2: нужен
только `paho-mqtt` и доступ к MQTT-брокеру.

Запросы состояния, истории и остановка с ожиданием ответа:

```bash
python3 ./LW-2/SCRIPTS/send_command.py status
python3 ./LW-2/SCRIPTS/send_command.py history --limit 10
python3 ./LW-2/SCRIPTS/send_command.py Stop
```

Эти команды работают и во время движения. `Stop` отменяет цель и ожидающие
шаги; отменённые задания получают `Status=2`, сама успешная остановка — `0`.
Если Nav2 не подтвердил отмену, ответ содержит ошибку и новые движения
блокируются до успешного повторного `Stop` с новым `Id`.

## Логистические процессы

На основе `sent_many_task.py` требуется реализовать два процесса:

1. Маршрут A: `S1 → T1 → way_a → T2 → S2`.
2. Маршрут B: `S2 → T2 → way_e → T1 → S2`.

После прибытия в точку загрузки отправьте `send_cargo_task("load")`, в точку
выгрузки — `send_cargo_task("unload")`; после каждой команды дождитесь
`wait_task_success`. Красный и синий треугольники обязательны; сообщения
в консоль дополняют их. Выбор маршрута можно организовать через консольный ввод. Фактические имена точек в коде должны соответствовать вашему файлу `points.txt`.

## Что включить в отчёт

- окно Gazebo после запуска симуляции;
- полученную карту в RViz;
- содержимое `points.txt`;
- три примера перемещения по MQTT и принятые статусы;
- результат (снимок экрана консоли) запуска `sent_one_task.py`;
- код последовательного маршрута и положения робота в его точках;
- реализацию и результаты маршрутов A и B;
- красный треугольник загрузки, синий треугольник выгрузки и статусы этих заданий;
- выводы по работе.

Все запущенные процессы завершаются сочетанием `Ctrl+C` в соответствующих терминалах.


## Радиус прибытия к точке

В `SCRIPTS/lw2_config.json` задайте расстояние в метрах:

```json
"navigation": {
  "default_mode": "proximity",
  "proximity_radius": 0.30
}
```

В режиме `proximity` робот считается прибывшим в пределах этого радиуса,
без проверки конечного угла. Значение должно быть конечным числом больше нуля.
`S3_startNav.sh` читает JSON и переносит радиус во временный YAML Nav2.
Это работает также при запуске через `start_tb3.sh`, для прямых целей,
MQTT и RViz при выбранном режиме `proximity`. После изменения JSON
перезапустите навигацию. Пересборка workspace не требуется.
Редактируйте JSON в Ubuntu-копии, из которой запускается навигация.
Режимы `position` и `orientation` сохраняют свои допуски из YAML.
При ручном запуске Nav2 в обход `S3_startNav.sh` JSON не применяется.


### Очистка следов движения в симуляторе

Если накопившиеся следы мешают просмотру, после завершения движения можно
очистить их без перезапуска симуляции. В отдельном терминале Ubuntu выполните:

```bash
source /opt/ros/humble/setup.bash
source ./LW-2/ros2_ws/install/setup.bash
python3 ./LW-2/SCRIPTS/clear_navigation_trails.py
```

Программа удаляет существующие точки следа всех цветов. При следующих
перемещениях след снова появляется, если он включён. Робот, склад,
сохранённые точки и треугольники загрузки/выгрузки остаются на месте.
Симулятор Gazebo должен работать. При очистке во время движения новые точки
могут появляться уже в ходе очистки; удобнее выполнять её между заданиями.
Параметр `--trail НОМЕР_ВАРИАНТА` задаётся у `navigate_waypoints.py`,
MQTT-драйвера или `start_tb3.sh`, а не у MQTT-отправителей заданий.


### Режим прибытия по умолчанию

В `SCRIPTS/lw2_config.json` параметр `navigation.default_mode` задаёт режим:

| Значение | Условие прибытия |
| --- | --- |
| `orientation` | Достичь позиции и сохранённого направления робота |
| `position` | Достичь позиции без проверки конечного направления |
| `proximity` | Войти в радиус `navigation.proximity_radius`, без проверки направления |

По умолчанию сохранён режим `proximity`. Настройка применяется при новом
запуске прямой навигации, MQTT-драйвера, `S3_startNav.sh` и `start_tb3.sh`.
Для целей из RViz режим задаётся при запуске Nav2. После изменения JSON
перезапустите Nav2 и MQTT-драйвер; пересборка не нужна.
Явные `--mode`, `--orientation` и `--ignore-orientation` переопределяют режим
конфига для соответствующей программы. В shell-скриптах также поддерживается
`TB3_NAVIGATION_MODE` (приоритет ниже явных аргументов). Поле `Mode` в MQTT-задании
переопределяет режим драйвера только для этого задания; без него используется
режим драйвера. Отправители `sent_one_task.py` и `sent_many_task.py` без явного
режима оставляют этот выбор драйверу.


### Контроллер движения склада

`S3_startNav.sh` при создании временного YAML подключает штатный контроллер
Nav2 Regulated Pure Pursuit через `SCRIPTS/navigation_controller.py`.
Он сначала разворачивает робота вдоль пути, затем ведёт его по проходу.
Скорость профиля — до 0,15 м/с. Проверяющие модули прибытия остаются прежними:
режим и радиус берутся из `lw2_config.json` либо явного режима запуска.
Изменение применяется и при запуске через `start_tb3.sh`; пересборка не нужна.
На повороте после `p1` DWB мог выбирать почти нулевую скорость и повторять
восстановительные вращения, хотя глобальный путь был построен.

Сообщение `Transform data too old when converting from map to odom` означает,
что навигация использует устаревшие данные локализации. Проверьте поступление
`/scan`, `/odom`, `/clock` и TF, отсутствие второй симуляции и единую настройку
`use_sim_time`. После восстановления данных перезапустите Nav2 и задайте
текущую начальную позу. Не увеличивайте радиус прибытия для обхода этой ошибки.

# JSON MQTT-команды LW-2

Протокол сохраняет поля `Module.Type`, `Data.Task.Id/Type/Data/Status`.
Брокер, группа и имя задаются в `SCRIPTS/lw2_config.py` либо переменными
`TB3_MQTT_*`, описанными в README. Команды отправляйте без retain.
Драйвер подписывается и отвечает с QoS 1.

По умолчанию вход — `space_v21/devices/in/delivery/amr1_v21`, выход —
`space_v21/devices/out/delivery/amr1_v21`. Перед отправкой подпишитесь на выход.
`Name` должен совпадать с именем робота; `Name: "all"` допустим на его входе.
`Type` модуля — `delivery`. Формат XML не используется.

## Состояние и история

Запросы не создают задания и доступны во время движения:

```json
{
  "Module": {
    "Name": "amr1_v21", "Type": "delivery", "UID": 1001,
    "Data": {"Request": "status"}
  }
}
```

Ответ `Module.Data.StatusInfo` содержит:

| Поле | Значение |
|---|---|
| `DeviceStatus` | `0` — свободен, `1` — занят, `2` — движение заблокировано после ошибки Stop/связи с Nav2 |
| `Loaded` | Подтверждённое состояние груза |
| `CurrentPoint` | Последняя успешно достигнутая точка или `null`; это не текущие координаты |
| `ActiveTaskIds`, `PendingTaskIds` | Выполняющиеся и ожидающие задания |
| `WaitingForTaskId` | ID ещё не присланного преемника или `null` |
| `Stopping` | Выполняется ли Stop |

Запрос истории:

```json
{
  "Module": {
    "Name": "amr1_v21", "Type": "delivery", "UID": 1002,
    "Data": {"Request": "history", "Limit": 10}
  }
}
```

Ответ `Module.Data.History` содержит `capacity`, `count` и массив `Tasks`,
от последних завершений к ранним. У каждого результата есть `Id`, `Status`,
`Report`, `Loaded`, `Duration` (целые секунды), `CompletedAt` (Unix-миллисекунды)
и поля принятого задания. Активные и ожидающие задания в историю не входят.
`Limit` — положительное целое число, без него возвращается вся история.
Ошибка запроса возвращается в `Data.RequestError`; `Data.RequestUID` повторяет
UID запроса, чтобы отправитель мог сопоставить ответ.

Размер истории задаётся `mqtt_driver.py --task-history 100` (по умолчанию 100).
История и состояние груза хранятся в памяти и сбрасываются при перезапуске
драйвера. Повтор известного `Id` возвращает сохранённый ответ и не запускает
действие повторно. После вытеснения ID из истории эта защита перестаёт действовать.

## Point и режим прибытия

```json
{
  "Module": {
    "Name": "amr1_v21", "Type": "delivery", "UID": 1003,
    "Data": {"Task": {
      "Id": 201, "Type": "Point", "Data": "parking", "Mode": "orientation"
    }}
  }
}
```

| Mode | Условие прибытия |
|---|---|
| `position` | X/Y с допуском 0.03 м, без конечного доворота |
| `orientation` | X/Y с допуском 0.03 м и сохранённый в points.txt угол с допуском 0.1 рад |
| `proximity` | Радиус 0.3 м, без конечного доворота; по умолчанию |

Без поля `Mode` используется режим драйвера: стандартно `proximity`, а при
`mqtt_driver.py --orientation` — `orientation`. Явное поле `Mode` имеет приоритет.
Префикс имени точки не меняет режим. Допуски — условия Nav2, а фактическая
точность зависит также от карты и локализации.

## Загрузка, выгрузка и Stop

`Upload`/`Load` оставляет красный треугольник и включает красную накладку
робота. `Download`/`Unload` оставляет синий треугольник и снимает накладку.
Поля `Data` у грузовых команд могут быть пустыми. Как и раньше, отдельная
грузовая команда может выполняться во время одиночного движения к Point.
В цепочке грузовой шаг выполняется последовательно после предыдущего шага.

Остановка — отдельное задание с новым ID:

```json
{
  "Module": {
    "Name": "amr1_v21", "Type": "delivery", "UID": 1004,
    "Data": {"Task": {"Id": 202, "Type": "Stop", "Data": ""}}
  }
}
```

Stop запрашивает отмену Nav2, ждёт завершения цели, обнуляет скорости,
очищает costmap и отменяет активное задание и ожидающие шаги. Локализация
и состояние груза сохраняются. Уже отправленные операции визуализации Gazebo
не откатываются; их запоздалые ответы не меняют отменённые результаты заданий.
Успешный Stop получает `Status=0`, отменённые задания — `2`.
Если Nav2 не подтвердил отмену, Stop получает `2`, а новые действия
блокируются; повторите Stop с новым ID. Пока остановка не подтверждена,
`status` сообщает `DeviceStatus=2`.

| Task.Status | Значение |
|---|---|
| `0` | Успех |
| `1` | Принято, выполняется или ожидает предыдущего шага |
| `2` | Ошибка либо отмена |
| `3` | Робот занят/заблокирован; новое задание не принято |

Можно запросить результат известного задания сообщением `Data.Task: {"Id": 201}`.
Для неизвестного ID ответ содержит `Status=3`, `Report="task not found"`.
Числовые `Module.Status` и `Task.Status` имеют разные назначения.

## Цепочка одним JSON-сообщением

`Data.Tasks` — массив последовательных заданий. Без ссылок порядок совпадает
с порядком массива:

```json
{
  "Module": {
    "Name": "amr1_v21", "Type": "delivery", "UID": 1005,
    "Data": {"Tasks": [
      {"Id": 301, "Type": "Point", "Data": "loading"},
      {"Id": 302, "Type": "Upload", "Data": ""},
      {"Id": 303, "Type": "Point", "Data": "shipping", "Mode": "orientation"},
      {"Id": 304, "Type": "Download", "Data": ""}
    ]}
  }
}
```

При явных `NextTaskId` порядок задаётся ссылками независимо от расположения
элементов массива. Последний шаг не содержит `NextTaskId` либо содержит `-1`.
Все ID должны быть разными и образовывать одну цепочку без циклов.
Stop передаётся отдельно и не может быть шагом цепочки.

Следующий шаг запускается после успеха предыдущего (`Status=0`). Ошибка
отменяет остаток цепочки с `Status=2`. Наличие точек и готовность Nav2
проверяются при выполнении шага. Максимум принятых активных и ожидающих
заданий — `--max-tasks 100`. Несвязанные новые задания во время цепочки
отклоняются как занятость, а `status`, `history` и Stop остаются доступны.

Преемника можно прислать отдельно: сначала Point с `NextTaskId=402`, затем
задание с `Id=402`. Пока оно не пришло, робот ждёт его без тайм-аута; Stop
отменяет ожидание. Для повторной доставки пакета используйте те же ID и новый
UID; смешивать известные и новые ID в одном пакете нельзя.

`sent_many_task.py` содержит редактируемую функцию `main()`. Класс `TaskClient`
вынесен в `task_client.py` и подключается строкой `from task_client import TaskClient`.
Консольный `sent_many_task_cli.py` принимает имена точек и операции `up`
(Upload) / `down` (Download) в одном списке и ждёт ответа после каждого шага.
Например: `S2 T1 up T2 down S2`. Для программирования доставки используйте
TaskClient и изменяйте `main()` основного примера. В начале `sent_many_task.py`
задайте `MQTT_BROKER`, `MQTT_PORT`, `WORKSPACE` и `MODULE_NAME`; они передаются
в `TaskClient(...)`. Для CLI доступны `--broker`, `--port`, `--workspace`, `--name`.
Настройки должны совпадать с MQTT-драйвером в Ubuntu.

## Команды терминала

```bash
python3 ~/LW-2/SCRIPTS/send_command.py status
python3 ~/LW-2/SCRIPTS/send_command.py history --limit 10
python3 ~/LW-2/SCRIPTS/send_command.py Stop
python3 ~/LW-2/SCRIPTS/sent_one_task.py parking --orientation
python3 ~/LW-2/SCRIPTS/sent_many_task_cli.py parking shipping parking --mode position
```

Каждый новый Stop получает новый ID автоматически. Отправители требуют
Python и `paho-mqtt`; ROS нужен только драйверу и непосредственному Nav2-отправителю.
